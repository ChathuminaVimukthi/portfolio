## Problem

We had four environments and no single place to see what was running where. Deployment status lived in Azure DevOps pipelines, service health was buried in Azure Monitor, and release blockers were tracked in a spreadsheet someone had to manually update. The result was a recurring question in standups — "is that deployed to staging yet?" — and too much time spent chasing answers that should have been obvious.

## Approach

I scoped this as a small internal tool rather than a full platform. The goal was to pull deployment events from the Azure DevOps API, correlate them with environment health checks, and surface a single status view that anyone on the team could glance at. We kept the scope tight: no release management, no approval workflows, just visibility. Getting something running in two weeks mattered more than building the right abstraction upfront.

## Tech Stack

The backend is a .NET 8 minimal API that polls the Azure DevOps REST API on a schedule and caches results in PostgreSQL — mostly so we could query history without hammering the DevOps API every page load. The frontend is React with a simple polling mechanism (no websockets; the data doesn't need to be that fresh). Everything runs as an Azure Container App behind internal DNS, so it's only accessible on the company network.

## Key Learnings

The Azure DevOps API surface is wider than it looks, and the data model for deployments is surprisingly non-obvious — environments, stages, and runs are separate concepts that don't join the way you'd expect. We spent more time on data normalisation than on the UI. The other thing I didn't anticipate: once the dashboard was live, the team started asking for things we hadn't considered — filtering by service, a way to see the last five deploys for a given environment. Shipping early made the real requirements visible.

## Tradeoffs

Polling instead of webhooks keeps the architecture simple but means there's a 30-second lag between a deployment completing and the dashboard reflecting it. That's fine for our use case — nobody is watching this in real time during a deploy — but it would matter if we ever needed incident response tooling out of the same data source. The other tradeoff was PostgreSQL for what is essentially a read-heavy, append-only dataset; a time-series store would be more appropriate at scale, but the operational overhead wasn't worth it for a tool with a handful of users.
